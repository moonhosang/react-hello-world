# 0단계 · 왜 리액트일까? — 반응형 vs 명령형

> 📂 이 강의의 파일
> - `public/vanilla/step0-why-react/counter.html` — **옛날 방식**: 순수 HTML + DOM (리액트·JSX·ref 전혀 없음)
> - `OldWayCounter.jsx` — 위 HTML을 `<iframe>`으로 띄우는 얇은 껍데기
> - `ReactWayCounter.jsx` — **리액트 방식**: 상태(state)로 관리
> - `index.jsx` — 둘을 나란히 비교하는 화면
>
> 왼쪽 카드는 리액트 파일이 아니라 **진짜 순수 HTML 파일**을 그대로 띄운 것이다.

리액트를 배우기 전에 **딱 하나의 문장**만 이해하면 된다. 나머지는 전부 이것의 확장이다.

---

## 1. 대전제 — UI = f(State)  (화면은 상태의 투영이다)

화면(UI)은 독립적으로 존재하는 무언가가 아니다.
**내부 데이터(상태, State)가 눈에 보이게 표현된 결과물**일 뿐이다.

```
UI = f( State )
화면 =  상태를 넣으면 나오는 함수의 결과
```

여기서 딱 두 가지만 따라 나온다.

- **같은 상태 → 같은 화면.** 화면은 상태만 보면 결정된다.
- **화면을 바꾸고 싶다? → 상태를 바꾼다.** 화면을 직접 손대지 않는다.

이 한 줄이 리액트의 전부다. 앞으로 배울 모든 것(`useState`, `props`, 렌더링)은 이 아이디어의 확장이다.

---

## 2. 두 가지 방식 — 명령형 vs 선언형

### 😵 명령형 (jQuery / 순수 DOM) — "어떻게(How) 바꿀지 내가 지시한다"

값이 바뀌면 **화면의 그 요소를 직접 찾아서** 손으로 바꾼다.

```
상태 변경 발생 ──▶ 개발자가 직접 DOM을 찾아 수동 변경 ──▶ 화면 업데이트
```

```js
// 순수 DOM / jQuery 방식
let count = 0

button.addEventListener('click', () => {
  count = count + 1
  document.querySelector('#value').textContent = count  // 👈 직접 찾아서 바꾼다
})
```

- 상태 변경과 DOM 변경이 **강하게 결합(coupling)** 된다.
- 처음엔 직관적이지만, 규모가 커지면 "어디를 어떻게 바꿔야 하는지" 관리 지점이 **폭발한다.**

### ⚛️ 선언형 (리액트) — "어떤(What) 화면이어야 하는지만 묘사한다"

상태에 따른 **최종 결과물(JSX)** 만 적어 둔다. 갱신은 리액트가 알아서 한다.

```
상태 변경 발생 ──▶ f(State) 재실행 ──▶ 바뀐 부분만 자동 계산 ──▶ 화면 반영
```

```jsx
const [count, setCount] = useState(0)

<button onClick={() => setCount(count + 1)}>+</button>
<span>{count}</span>   // 👈 count가 바뀌면 이 자리는 자동으로 갱신
```

- `document.querySelector`도, `textContent = ...`도 **없다.**
- 개발자는 DOM을 직접 건드리지 않고 **상태 관리에만 집중한다.**

| | 명령형 (옛날) | 선언형 (리액트) |
|---|---|---|
| 관점 | **어떻게** 바꿀지 절차 | 화면이 **어떤 모습**인지 결과 |
| 화면 갱신 | 내가 직접 DOM 조작 | 상태만 바꾸면 리액트가 담당 |
| 규모가 커지면 | 갱신 누락 버그 폭발 💥 | 상태만 맞으면 화면은 항상 일치 ✅ |

## 3. 왜 리액트 같은 게 등장했나? — 상태 추적 불가능 문제

리액트가 나온 진짜 이유는 단순히 **"DOM 조작이 느려서"가 아니다.**
앱이 커지면 사람이 **상태를 더 이상 추적할 수 없게 되기 때문**이다.

```
[2000년대 jQuery 시대]
이벤트 발생 ─▶ DOM A 수정 ─▶ A를 만지다 DOM B에 영향 ─▶ B가 다시 DOM C 수정 ...
( 어디서 무엇이 바뀌었는지 추적 불가 = '스파게티 코드' )
```

두 가지가 특히 사람을 무너뜨린다.

- **상태 동기화 실패(State Desync)** — 하나의 상태가 화면 3~4곳에 영향을 줄 때,
  명령형에서는 그 3~4곳의 DOM 수정 코드를 **개발자가 빠짐없이** 써야 한다.
  하나라도 놓치면 데이터와 화면이 어긋나는 버그가 난다.
- **Side-effect 통제 불능** — DOM 자체가 데이터 저장소 역할까지 겸하면서,
  UI 조작이 또 다른 UI 조작을 부르는 **꼬인 의존성**이 생긴다.

리액트는 **"상태만 맞으면 화면은 언제나 상태와 일치한다"** 를 보장해서, 이 문제를 통째로 없앤다.

## 4. 🧠 한 걸음 더 — 가상 DOM (지금은 몰라도 된다)

> 이 절은 원리가 궁금한 사람을 위한 심화다. 당장 몰라도 실습에는 지장 없다.

"화면 전체를 새로 그리듯" 코드를 짜는데 왜 안 느릴까?
리액트는 실제 DOM을 통째로 갈아엎지 않기 때문이다.

1. 상태가 바뀌면 새 화면 명세를 **가상 DOM**(메모리 상의 가벼운 객체 트리)으로 만든다.
2. 이전 가상 DOM과 새 가상 DOM을 **비교(Diffing)** 해서 진짜 바뀐 곳만 찾는다. → **재조정(Reconciliation)**
3. 그 **최소한의 차이만** 실제 DOM에 한 번에 반영한다. (Batch)

핵심: 가상 DOM의 진짜 가치는 "속도"보다 **예측 가능성과 생산성**이다.
전체를 다시 그리듯 단순하게 써도 리액트가 알아서 최소 조작으로 바꿔주니,
개발자의 **인지 부하가 비약적으로 줄어든다.**

---

## 한 줄 요약

> **화면 = 상태의 결과물(UI = f(State)).**
> 명령형은 상태가 바뀔 때마다 사람이 DOM을 직접 찾아 고치고,
> 리액트는 상태만 바꾸면 바뀐 곳을 알아서 반영한다.
> 웹 앱이 복잡해져 "데이터와 UI 동기화"를 사람이 감당할 수 없게 된 것이 리액트가 나온 이유다.
